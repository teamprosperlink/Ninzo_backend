- Date: 2026-11-06
- Branch: `feat/38-session-system`
- Reviewer: independent Claude subagent, two rounds

## 1. Scope
Step 4 of the `v0.2.0` plan on #25: `internal/identity` with access and refresh tokens, renewal, sign-out, ending sessions, and keeping user types apart. `customer-api` and `rider-api` serve `refreshToken` and `signOut`. New: `signOut` in both contracts and the mock, migration 0009, and the `JWT_*` settings.

**Not covered:** no sign-in endpoint exists yet, so nothing starts a session outside tests. Rate limiting is #39. Migration 0009 is not on Supabase.

One missed break showed that a test never exercised the refresh lock, and two hung on failure: those tests were strengthened, and the breaks were then caught with a clear failure.

## 4. Manual / end-to-end validation
Real programs on local Postgres, on the first design:
```
first refresh: [200], expires_in_s 900

customer token signing out on the rider API: 401
normal renewal: [200]
sign out with no token: 401
the replaced token comes back: [401] unauthorized
```

**The rules for a replaced token changed afterwards**, so the last two lines no longer describe today's behaviour. The later design is covered by the tests in section 3, and was not re-run with the real programs.

## 6. Known limits, for later steps
- **Sign-in must take a per-actor lock**, before checking credentials, and `EndAll` must too. Otherwise a sign-in in progress during a password reset keeps its session (reproduced). Recorded on #25.
- **Suspend and block code must call `EndAll`.** A status change alone leaves a token that was not presented working again once it is lifted (reproduced).
- **Rate limiting must be per chain, as well as per IP** (#39). Repeating a used token adds a row each time.
- Access tokens work for up to 15 minutes after a sign-out or a reset. Endpoints with sensitive actions must also check status.
