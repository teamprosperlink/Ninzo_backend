# Test report: #134, console sign-in, users, permissions, approvals and flags (v0.9.0 part B)

Date: 2026-11-11. Local Postgres only. Migration 0035 is not on Supabase.

## What was built
- `apps/console-api` (port 8083) and `cmd/console` (`add-admin`, `reset`; `-local` or `-remote`).
- Sign-in: ID and password (PBKDF2-SHA256, 600k rounds), then a TOTP code (RFC 6238, ±1 step, no replay). First sign-in enrols the authenticator; a temporary password must be changed before anything else.
- Lockout: 5 wrong passwords or codes in 15 minutes lock for 15 minutes; a locked account answers exactly like a wrong password. Per-address limits on the sign-in steps.
- Roles and permissions checked on every call from a fresh read; 403 names the missing permission.
- Users: list, create, update, reset; the last-admin and self-removal guards; deactivation and role change end sessions through the session lock and end open challenges; deactivation cancels pending approvals.
- Approvals: request, approve by someone else, reject, cancel by the requester, lapse after 24 hours, fail as stale. Feature flags are the first kind.

## Deliberate breaks (20 run, each reverted)
Caught: wrong codes not counted toward the lockout; the lock revealed to the right password; no lockout; a challenge kept after a reset; approvals kept after deactivation; no temporary-password gate; no permission check; approving your own change; a stale flag change applied; a TOTP code replayed; enrolment skipped; self-removal; sessions kept after deactivation; both guess limits removed together (12 codes checked on one challenge).

Not caught alone, because a second layer covers the same failure:
- Widening only the per-challenge attempt cap: the account lockout still stops guesses at 5. Removing both is caught.
- Disabling the last-admin guard: the permission check before the transaction already refuses an admin who was just deactivated. The guard covers two admins removing each other at the same moment. The race test (`TestTwoAdminsCannotRemoveEachOther`) checks that exactly one admin remains, but cannot force that timing, so the guard was checked by reading the code.

## Independent review
3 FAILs, all fixed: no sign-in rate limit, and a lockout that leaked which password was right; no account-wide cap on TOTP guesses, and an attempt counter that could be raced; sessions ended without the session lock. Notes taken: open challenges end on reset, deactivation or password change; pending approvals are cancelled on deactivation; the password is checked before the row lock; enrolment is audited; the otpauth URI is escaped; contract text corrected. Recorded in known_downsides: an admin can make a second admin and so bypass the two-person rule; first sign-in is trust on first use.

Result: PASS
