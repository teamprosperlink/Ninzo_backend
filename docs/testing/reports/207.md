## 1. Scope
- **Migration 0050:**
  - `location_pings.cell` holds the `blr76` grid cell of each new ping, or null beyond the grid's reach. Old pings stay without one, because the table is append-only.
  - `rider_positions` holds one row per rider, with RLS on.
- **`internal/riderpos`:**
  - `Cell`.
  - `Record`: an upsert that moves the row only when the ping is newer by device time.
  - `Latest`.
  - `TierFor`: which tier of a gate version's newest build the rider's cell is in, with the position's age (by device time). It answers "beyond" when the rider is outside the build or off the grid.
- **`orders.pingTx`** (shared by the live ping and the offline batch) now inserts the ping with its cell and calls `riderpos.Record` in the same transaction. Nothing else in tracking changed.
- **Lists updated:** the data map (a table row, plus the writes of `locationPing` and `sendEventBatch`), `builtInV100`, and the package lists in the Taskfile and CI.

## 2. Commands run and raw output
`go test -count=1 -p 1 -timeout 30m ./internal/orders/ ./internal/riderpos/` on 5433. Every existing `orders` test passed unchanged. The one failure was the new test:
```
--- FAIL: TestPingsKeepACellAndMoveTheRidersPosition (7.78s)
    positions_test.go:29: after a live ping: 12.9355 2026-11-13 04:32:19.844286 +0530 IST ...
FAIL	github.com/teamprosperlink/Ninzo_backend/internal/orders	1098.151s
ok  	github.com/teamprosperlink/Ninzo_backend/internal/riderpos	13.827s
```

The cause was in the test: the database keeps device times to the microsecond (as `tracking.go` notes), and the test compared them with a clock carrying nanoseconds. It now compares at microseconds, and three runs in a row pass:
```
ok  	github.com/teamprosperlink/Ninzo_backend/internal/orders	7.778s
ok  	github.com/teamprosperlink/Ninzo_backend/internal/orders	7.962s
ok  	github.com/teamprosperlink/Ninzo_backend/internal/orders	7.829s
```
The `riderpos` tests (`TestCellIsTheGridCellOrNone`, `TestThePositionFollowsTheNewestPingOnly`, `TestTierForPlacesTheRiderAroundTheGate`) pass, and so do `tests/contracts`.

What the tests check:
- A live ping stores its cell, and the position equals it.
- An older ping sent later in the offline batch is kept but does not move the rider, and neither does the same device time again.
- A newer batch ping does move the rider.
- Every new ping has a cell.
- A point 1,700 km away has no cell.
- `TierFor` answers each case: no position, no build, at the gate (sweet spot and timer zone), 1 km away (outer ring), and 3 km away (beyond, not in the set).

## 3. Deliberate breaks
Each break was made alone, the tests run, then the code restored (checked with `cmp`).

| Break | Caught by |
|---|---|
| A late ping moves the rider back (no device-time guard) | `position {Lat:12.99 ...}`, the late ping's point |
| `TierFor` ignores the cell set | `at the gate: {... Reach:beyond ...}` |
| The ping path skips `Record` | `positions_test.go:27: no rows in result set` |
| No future-time guard | `after a ping a day ahead: {Lat:12.99 ...}` (the position froze) |
| Age by received time | `age 0s, want 5m` |

## 4. Independent review
- **First pass: FAIL.** Findings, all fixed or recorded:
  1. **A ping with a future device time froze the position for good** (high). `Record` now skips pings more than `FutureLimit` (30 s, as tracking uses) ahead of arrival. They are kept in `location_pings` but do not move the rider. Tested, with a break that was caught.
  2. **Age understated staleness after an offline flush.** It now counts from the device time. Tested.
  3. **Test gaps:** the future-time and age tests are added, and the equal-device-time rule (the first received stays) is documented. The no-offer ping branch reaches the same `Record` call after the order switch, and is covered through `Record` directly.
  4. **Privacy:** there is no rider erasure flow yet, and the foreign key refuses deleting a rider with a position. Recorded in `known_downsides.md`.
  5. **Two meanings of "latest":** the live map reads by received time, `rider_positions` by device time. Recorded in `known_downsides.md`.
  6. **Cost:** `TierFor` loads the gate's whole cell set per call. Fine for 8 riders; matching (W5) should cache per gate.
- **Second pass:** PASS. Its minor points are fixed: a negative age (a clock up to 30 s fast) is clamped to 0, and a rider whose clock runs further ahead is recorded in `known_downsides.md`.

## 5. Known limits
- Pings stored before this change have no cell.
- `rider_positions` is one updated row per rider, fine for the pilot. At city scale it moves to Redis (G17).
- The console live map still reads pings itself. A read function for it is W3 step 4, by agreement with the console session.
