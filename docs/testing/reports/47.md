# Test report: Google sign-in, phone verification and account merging (#47)

- Date: 2026-11-06
- Branch: `feat/47-google-signin`
- Reviewer: independent Claude subagent, two rounds

## 1. Scope
`signInWithGoogle`, `requestPhoneOtp` and `verifyPhone` on `customer-api`. Riders do not use Google. Accounts merge only on a phone proven by OTP.

**Not covered:** a real Google login, which needs the app on staging. Tests use fake tokens signed the same way, with a fake key server. Telling a phone about a link is queued in the outbox, but nothing delivers it until the worker and real SMS exist. Unlinking is #48. IP rate limiting is #39. Apple comes later. Nothing changes on Supabase.

## 3. Scenario results
| Rule | Tested |
|---|---|
| A wrong audience, issuer, signer, algorithm, or no expiry or subject is refused | Yes |
| An unverified email is not kept, and a matching email never merges accounts | Yes |
| Google's keys are cached, rotate, and bad traffic cannot hammer Google | Yes |
| A Google outage is never a refusal, and known keys keep working | Yes |
| A hanging Google holds up nobody with a known key, and one cancelled request harms nobody | Yes |
| A first sign-in creates an account with no phone, and a double tap makes one person | Yes |
| Verifying a new phone ends the old tokens, and tells the phone about the link | Yes |
| A different phone on a verified account is refused | Yes |
| A phone with a customer merges into it, so `customer_id` changes, and that phone's other devices carry on | Yes |
| A phone with only a rider gets the customer moved onto that person | Yes |
| A phone with a different Google account is refused | Yes |
| A block during a merge leaves everything alone, and a blocked owner stops a merge | Yes |
| A merge is traceable for good: the removed customer, person and Google account are recorded | Yes |
| A code works only for its purpose, and only in the session that asked | Yes |
| An old token cannot send a code after a merge or a block | Yes |
| Two accounts racing for one phone: one wins, and the other is told properly | Yes |

**Deliberate breaks:** all caught or explained. Two are stopped by a second layer: the JWT library refuses other algorithms by itself, and refresh refuses a profile that no longer exists. One guards a path that cannot happen today. Races first caught only by luck now have tests that force them.

## 6. Known limits, for later steps
- **Merge takeover:** an intercepted or read-out code gives lasting access until unlinking exists (#48). Must be done before launch.
- **Any future block or suspend code** must take the actor lock before changing a status, in the same order as `merge`.
- **The code's wording** needs a second DLT template, recorded in `sms_setup.md`.
- **A merged customer's name** is lost, by design, because an unverified customer holds nothing else.
