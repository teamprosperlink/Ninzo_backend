## 1. Scope
- **`internal/matching`** is pure, with no database or network:
  - `ByStraightLine`: today's order, nearest node first, ties by scooter id.
  - `ByRoad`: the fastest by road from each candidate's position. Unreachable candidates go last, in today's order. Placeholder or mismatched legs return today's order and `false`.
  - `Sources` and `IDs`.
- **Migration 0051** adds `matching_by_road`: 0 or 1, **0 by default**, with zone override rows left as they were (as 0049).
- **`availability.PickScooterExcept`** keeps every filter: zone, sale hours, reach, stock, locks and excluded scooters. With `matching_by_road` = 1, more than one candidate left after busy and excluded scooters are removed, and a routing client set, it reorders them with one `Table` call from each rider's live position (`rider_positions`, if it reached the server within `signal_release_s`), or from the scooter's node when the position is stale.
  - A routing error or a placeholder answer keeps today's order.
  - The stock check, lock and "one scooter locked" rule then run in the new order, unchanged.
- **`availability.ConfigureRouting(os.Getenv)`** runs at start-up in the customer API, the only one that places and dispatches orders, inside `Validate`. An empty `ROUTING_ENGINE_URL` keeps straight lines; a malformed URL fails the start.

`TestMatchingByRoadPicksTheFasterRider` uses two scooters. The first is 220 m north of the customer, nearest by line but 200 s by road. The second is 300 m south and 50 s by road. The test checks:
- **Setting 0:** the first scooter is picked, with no routing call.
- **Setting 1:** the second is picked, with one call.
- **The second rider's ping goes stale:** their node (300 s) is used, so the first is picked.
- **Routing answers placeholders:** the first is picked.
- **No routing client:** the first is picked.

The full run over availability, geo, orders, tests/db and cmd/settings with the setting at 0 is in section 5.

## 3. Deliberate breaks
Each break was made alone, the tests run, then the code restored (checked with `cmp`).

| Break | Caught by |
|---|---|
| Placeholder legs trusted | `placeholder: [a b] true, want today's order and false` |
| Unreachable not last | `[near far], want the unreachable one last however near`. It was not caught at first; that case was added, then the break re-run |
| Straight-line ties by id reversed | `[d b a c], want nearest node first, ties by id` |

## 4. Independent review
PASS, with points that are all taken:
1. Only the customer API dispatches, so the start-up hook is now there alone. In the rider and partner APIs it did nothing, and a bad URL would have stopped them starting.
2. Ordering now runs after busy and excluded scooters are removed, so dispatch never routes to busy ones and makes no call with one candidate left.
3. Freshness uses `received_at` (the server's clock), not the device time.
4. New cases: routing returning an error, and answering for fewer riders, both keep today's order.
Not changed: the routing call runs while the order row is held (and, on a gate change, the old scooter's stock rows). It is bounded by the 300 ms timeout and the breaker, with the setting off by default.
