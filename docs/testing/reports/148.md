# Test report: console incidents, the server side (#148)

Date: 2026-11-12. Local Postgres only. Migration 0044 is not on Supabase. Independent review: not yet done (to be run before the PR).

## What was built
- `migrations/0044_incidents.sql`: tables `incidents` and `incident_notes`; `problem_reports.handled_at`; five trigger functions and four triggers; a backfill. It starts with one `LOCK TABLE` of the referenced tables (`orders`, `riders`, `console_users`, share row exclusive) and one of the altered ones (`problem_reports`, `support_tickets`, `arrival_reviews`, `outbox_events`, access exclusive), in a fixed order, as 0042 does. Down does the same.
- `internal/console/incidents.go`, mounted by `MountIncidents` in `apps/console-api/main.go`: `listIncidents`, `getIncident` (permission `incidents.read`), `assignIncident`, `addIncidentNote`, `closeIncident` (`incidents.manage`). Every write needs an Idempotency-Key, is audited, saves its reply in the same transaction (`change`), and locks the incident row (`FOR UPDATE`).
- The mock (`internal/mockserver/console.go`) already served the five operations from the contract part; its list gained a `signal_lost` sample.
- `tests/db/migrations_test.go`: `incidents` and `incident_notes` added to the built v0.10.0 tables, as #159 did.

## How incidents come to exist (the choice)
Database triggers, in the same transaction as the source row, plus a backfill in the migration. Not a background pass, not Go code at each write.
- The data map had planned a background task (`open_incidents`). A pass leaves a gap in which a source exists with no incident, and needs a runner in console-api, which has none.
- Writing the incident from Go at each source touches `internal/orders` in five places (batch.go, problems.go twice, remedies.go, support.go) and fails the next time someone adds a sixth. It also forces the 18-minute orders suite. A trigger covers every writer, including the timeout paths, with no change to `internal/orders`.
- Exactly once: `UNIQUE (kind, source_id)` and `ON CONFLICT DO NOTHING`. A lost signal (problem report and support alert) is one incident: the alert skips when a system lost-signal report exists for the order, and a partial unique index allows one open `signal_lost` per order. Every other kind is one incident per source row; the contract says "per order and kind", which holds for lost signals only (recorded in `known_downsides.md`).
- A stray id in an alert's payload (not a uuid, or an order that does not exist) is stored as null; it can never stop the source row being written.
- Resolving the source closes the incident: ticket `open` to `resolved` (`closeTicket`) and review `open` to anything else (`decideArrivalReview`, or the timeout), by the same triggers, with `closed_by` null.

## Closing, and the #138 downside
A support alert is a row in `outbox_events` (topic `support.alert`) that no worker takes, so it sat undelivered in the due index. Closing its incident sets `delivered_at`, which takes it out of that index; that is the fix, and the row is removed from `known_downsides.md`. A problem report's incident sets `problem_reports.handled_at` (new). A lost signal's incident marks its reports and every lost-signal alert for the order. A ticket or review is never written from the queue: `source_open` (409) while it is open, as the contract says. A closed incident is `incident_closed` (409) for assign, note and close.
Side effect: the daily purge deletes delivered events after 7 days, so a handled alert leaves `listSupportAlerts` then; the incident stays (known downside).

## Tests added

- One incident per source: a ticket, a review, a problem report, a handover alert and a lost signal with its alert make five incidents, not six; a second lost signal on the same order, a push event, a resolved ticket and an alert with stray or no ids behave as described above; order and rider are kept (a review carries its order's rider).
- List: newest first, paging by two with no repeats, `kind` and `status` filters (also together), bad status, kind, limit and cursor are 400, `notes_count`, contract check (`IncidentList`).
- Detail and privacy: every incident against `IncidentResponse`; the list and every view hold none of the customer's words, flat, phone, the rider's note, or any phone digits; notes are shown oldest first with their author, and not in the list; unknown and malformed ids are 404.
- Assign: to ops and to oneself, again to the same person, unassign (back to open), unassign when already open; inactive user, hub manager (no permission) are 409 `user_cannot_take`; unknown user 404; malformed, number, missing and empty bodies 400; a refused call changes nothing; four audit rows; a closed incident is 409 `incident_closed` for both; unknown incident 404.
- Notes: trimmed, 2000 characters allowed, empty, blank, 2001, missing, wrong type and NUL are 400; refused notes are not stored; audit holds the note id and not the words; a note on a closed incident is 409; notes stay readable after closing.
- Closing: a support alert is marked delivered (and only that one: a second alert, a lost-signal alert and a stray one are not); a problem report gets `handled_at` (not the lost-signal report); a lost signal handles its reports and alerts for the order and not another order's; a new lost signal after the close opens a new incident; audit with the reason; a second close is 409; bad reasons are 400.
- Ticket and review: closing by hand is 409 `source_open`, changes nothing; `closeTicket` closes the ticket's incident (not by a person), `decideArrivalReview` closes the review's, a timed-out review closes its too, an assigned incident closes with its source and keeps its assignee; then notes and close are 409.
- Permissions: a hub manager gets 403 naming `incidents.read` for the two reads and `incidents.manage` for the three writes; no token is 401; support, ops and admin pass.
- Replay: the same key and body answers the same with one note and one audit row; the same key with another body is 422; no key is 400; a replayed close is the first answer.
- Concurrency: six people close one incident at once (one 200, five 409, one audit row); and a held row lock: with another transaction holding and closing the incident, an assign, a note and a close all wait (nothing answers for 1.5 s), then each is 409.
- Backfill: the migration's own backfill statements, read from the file, are run on a wiped database (and twice in a row): they make the open incidents and none for a handled alert or report, a closed ticket or a decided review; order, rider and `opened_at` are kept. `tests/db`: a database at migration 43 with an open and a resolved ticket, two reports, and alerts (one stray, one delivered, one not an object, one push) gets exactly the right five incidents by applying 0044; a new report then opens one; the table checks refuse an assigned incident with nobody and a closed one with no time.

## Independent review
A separate reviewer found no way for the triggers to fail or roll back a write on the order, rider or customer path. It raised these points:
- **Fixed: the backfill would have flooded staging.** Before 0044 nothing marked problem reports or support alerts handled, so every one ever made looked open. The migration now settles those whose order has ended, and those with no order that are over a day old, before the backfill. Test: `TestMigration0044SettlesWhatIsOld`. Removing the settle step makes it fail.
- **Fixed: the contract wording.** It now says one incident per source, except lost signals (one per order, showing the first report's rider). Closing never reopens or edits a ticket or review, and it marks alerts and reports handled, which the code does.
- **Fixed: the lost-signal close.** An index on open support alerts by `order_id` serves its update.
- **Kept, in known_downsides:** an assignee who is later deactivated stays assigned; writes by a role other than the service role would fail in the trigger.
