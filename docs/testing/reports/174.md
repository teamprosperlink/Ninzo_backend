# Test report: the staging database moves to Singapore (#174)

## The problem
The customer app team measured staging writes at 1 to 3.6 s (create order 3.6 s, handover 3.2 s, accept 2.5 s, payment 2.3 s) and reads at 0.4 to 0.6 s. The APIs run on Railway in Singapore, which has no India region, and the database was Supabase in Mumbai. A write runs 20 to 35 database statements one after another, and each one crossed the region (about 60 to 150 ms).

## What was done (2026-11-13)
- The owner chose a new Supabase project in Singapore. The free plan allows two active projects, so the Mumbai project `chyejfgsipcsdxnginei` was paused (kept for 90 days as a backup). The other product's project was not touched.
- New project: `ninzo-staging-sg`, ref `xzndsqckkywmcobdeuep`, region ap-southeast-1.
- The project guard `internal/dbtarget.NinzoRef` was pointed at it (#231, PR #232).
- The owner ran migrations 0001 to 0054 and `task staging:testdata`. They set the `ninzo_service` password and Railway's customer-api `DATABASE_URL` (the `ninzo_service` login).
- rider-api, partner-api and console-api now read `DATABASE_URL` as a Railway reference to customer-api, so it is set in one place.
- All four APIs were deployed from ecd73fa.
