# Test report: streams outlive the server's limits (#90)

- Date: 2026-11-09

## Scope
Found in the `v0.5.0` staging run: both live streams were lost about 30 seconds after connecting. Every `/v1` request had a 20-second context, and the server's read and write timeouts stayed on the connection after the stream took it over. The stream tests used test servers with no timeouts, so they missed it.

Fix: a WebSocket upgrade skips the request limit, and `httpserver.ForStream` clears the connection's deadlines before the stream takes it over.

## Commands run
```
$ go test -count=1 -run TestAStreamOutlivesTheRequestLimits ./internal/platform/httpserver/
$ go test -count=1 -p 1 ./internal/platform/httpserver/ ./internal/orders/
```

## Scenarios
| Rule | Tested |
|---|---|
| On the real server, a stream reads after the 15 s read timeout and writes after the 25 s write timeout, with its context still live past 20 s | Yes |

**Deliberate breaks:** 3. Removing the request-limit skip was caught: the context ended at 20 s. Removing either deadline clear was not caught: Go clears both deadlines itself when a connection is taken over, so `ForStream` is kept only as a safety net. The real cause on staging was the request limit.
