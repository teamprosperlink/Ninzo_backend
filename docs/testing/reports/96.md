## Scenarios
| Rule | Tested |
|---|---|
| A breakdown before the customer saw the rider: scooter out of service, silent rematch (no `seq`), the rider sees `reassigned`, the hold moves to the working scooter, the report and note are kept | Yes |
| An accident after the customer saw the rider: the order fails, full refund `order_failed`, stock given back | Yes |
| Gate closed, customer absent, unsafe route: recorded only; another rider's order is refused; bad input is a 400 | Yes |
| On-time pings stop for 2 minutes: reassigned to the other scooter, with a support record; not before 2 minutes | Yes |
| A reassign after the customer saw the rider moves `seq` and shows looking_for_rider | Yes |
| No reassign while the timer runs (support alerted once), once the customer has the code, or for a rider who never pinged | Yes |
| A scooter in maintenance gets no offers, also when it broke before any offer | Yes |

**Deliberate breaks:** 18. 17 caught after one test was added and four invalid breaks were redone. Allowing reassignment while the timer runs was not caught alone: by then the code has been released, which also stops a reassignment.
