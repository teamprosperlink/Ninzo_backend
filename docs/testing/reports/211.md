## 1. Scope
**`availability.inReach`** is one function for both the pick (`PickScooterExcept`) and the menu (`At`), so they cannot disagree. It lists the scooters that can serve a point, in the order to try them:
- **Setting 0, or no routing:** today's rule exactly. The SQL `reachable` within `min(max_search_radius_m, speed × budget)`, ordered by node distance, then id. The list is kept as the query returns it, with no recomputation in Go.
- **Setting 1 with routing:** the query reaches out to `max_search_radius_m`. One `Table` call from each rider's live position (or the node when stale) keeps only those within `sweet_spot_budget_s` by road, fastest first.
- **Routing fails, or answers straight lines:** the list falls back to today's straight-line reach and order.

`At`'s stock query now takes the scooter ids from `inReach`. Its parameters are renumbered: zone, the ids, weekday, minute.

**Test changed:** `TestMatchingByRoadPicksTheFasterRider` (from #209) used road times past the 80 s budget (200 s and 300 s). This Issue makes the budget a filter, so those scooters are now refused by design. Its road times are moved inside the budget (70, 50 and 75 s), and it still checks the same orderings: on, off, stale, placeholder, error, short answer and no router. The rule changed in this Issue on purpose; the test was not changed to hide a failure.
