# Test report: security headers, vulnerability and secret scanning (#238)

## What was built
- **Security headers on every reply** of all four APIs and the health checks (`withSecurityHeaders` in `internal/platform/httpserver`):
  - `Strict-Transport-Security: max-age=31536000; includeSubDomains` (HSTS);
  - `X-Content-Type-Options: nosniff`;
  - `Cache-Control: no-store`;
  - `Referrer-Policy: no-referrer`;
  - `X-Frame-Options: DENY`;
  - `Content-Security-Policy: default-src 'none'; frame-ancestors 'none'`;
  - `Cross-Origin-Resource-Policy: same-site`.
- **CI `vulncheck`:** `govulncheck` fails the build on a known vulnerability in code we reach.
- **CI `secrets`:** gitleaks fails the build on a committed key, token or password.
- **Dependabot:** weekly update PRs for Go modules and GitHub Actions.
- **Go 1.27.3 to 1.27.4.** The first govulncheck run found **GO-2026-6859** (an HTTP/1 server crash, from a MaxBytesReader header race in net/http) in Go 1.27.3, reached from our servers. It is fixed in 1.27.4.

## Live check before the change
All four APIs served TLS 1.3 (TLS_AES_256_GCM_SHA384) with a valid certificate, and HTTP was redirected to HTTPS (301). There was no HSTS and no other security header. No IPv6 (AAAA) records: `*.up.railway.app` is IPv4 only. IPv6 comes with a custom domain behind Cloudflare, on the pre-launch list.

## CI fix
On CI, govulncheck v1.1.4 crashed while analysing for Linux (`panic: unexpected expr: *ast.KeyValueExpr` in golang.org/x/tools/go/ssa v0.29.0), a bug in the tool, not a finding. The job now uses govulncheck v1.9.0 (released 2026-10-11). Run locally with `GOOS=linux GOARCH=amd64`, as CI analyses, it gives: No vulnerabilities found.
