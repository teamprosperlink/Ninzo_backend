## Scenarios
| Rule | Tested |
|---|---|
| A queue flushed in order: late pings kept as evidence only, the handover applies with arrival from the handover; sending it again changes nothing | Yes |
| One bad event never blocks the queue: bad ids, bad payloads, unknown types, restock (`not_available_yet`, retryable), a wrong code (final, the attempt counted), then a good handover | Yes |
| Only final results are kept; a retryable rejection is checked again | Yes |
| A queued handover after a cancel gives `order_cancelled` | Yes |
| A direct request sent first with the event_id as its key counts once | Yes |
| Queued problems and scans apply; a bad scan is rejected `bad_scan` | Yes |
| Queued pings sent on time count; a queued handover is judged by its device time: an old one is accepted and flagged, a current one far from the gate is refused | Yes |
| A bad batch body is a 400 | Yes |

**Deliberate breaks:** 11. 10 caught after three tests were added and one invalid break was redone. Stopping the whole batch on one event's server error was not caught: no test can cause a server error inside one event.
