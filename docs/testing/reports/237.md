- Environment: Windows 11 (arm64), Go 1.27.3, geo Postgres on 5433; a fake Razorpay server in the tests (no real Razorpay call)

## 1. Scope
- **`orders.Razorpay` implements `Payments`.**
  - `NewOrder` calls `POST /v1/orders` with basic auth, the amount in paise and INR, and checks the reply's id and amount.
  - `Refund` first lists the payment's refunds. If one already carries our refund id in its notes, it reuses it; otherwise it calls `POST /v1/payments/{id}/refund` with that note.
- **`NewRazorpay(getenv)`:** keys are all or nothing, the webhook secret is required with them, and the key id must look like a Razorpay key. **`CheckRazorpayKeys`** refuses live keys outside production.
- **Webhook `POST /v1/webhooks/razorpay`:**
  - Body limit 256 KB. The HMAC-SHA256 signature is checked in constant time before anything else. `X-Razorpay-Event-Id` is required, and the event id is kept in `webhook_events`, so the first delivery is the one acted on.
  - `payment.captured` and `order.paid` store the Razorpay payment id and call `Confirm(paid)`. A row already failed is reopened when a later attempt on the same Razorpay order succeeds. A different amount is logged and not accepted.
  - `payment.failed` calls `Confirm(failed)`.
  - `refund.processed` and `refund.failed` settle the refund, matched by Razorpay's id or by our id in the notes.
  - Unknown events are kept and ignored. An error rolls back and answers 500, so Razorpay retries.
- **`SendRefunds` and `RunRefunds`** (every 30 s): pending Razorpay refunds with a payment id, 10 at a time, rows locked with `FOR UPDATE SKIP LOCKED`. On failure: attempts + 1, the last error kept, and the next try after 2^attempts minutes, at most 60.
- **customer-api:** Razorpay when the keys are set. The test-payment endpoint is mounted only without Razorpay, and the webhook and refund pass only with it.
- **Migration 0055:**
  - `payments.provider_payment_id`
  - on `refunds`: `provider_refund_id`, `attempts`, `last_error`, `next_try_at`
  - the `webhook_events` table
- **Docs:** `env.example`, real_and_stand_ins, known_downsides, the data map (`webhook_events` is now built in v1.0.0).

## 3. Deliberate breaks
Each break was made alone and caught, then the code restored (checked with `cmp`).

| Break | Caught by |
|---|---|
| Signature not checked | `TestABadWebhookChangesNothing` |
| Amount not checked | `TestAWrongAmountIsNotAccepted` |
| A failed attempt not reopened | `TestAFailedAttemptThenASuccessSecuresTheOrder` |
| No lookup before refunding | `TestACrashAfterSendingDoesNotRefundTwice` |
| Retry wait ignored | `TestARefusedRefundIsRetriedLater` |
| Payment id not kept | `TestACapturedPaymentSecuresTheOrderOnce`, `TestARefundIsSentOnceAndSettledByWebhook` |

Deduplication by event id cannot be broken visibly, because `Confirm` is itself idempotent (known_downsides).

## 4. Independent review
- **First pass: FAIL.** Two blocking findings, both confirmed by running them:
  - The retry wait overflowed an integer after 31 failures (`power(2,31)::int`), so one stuck refund would stop every later refund pass.
  - Razorpay sends `notes: []` when there are none, which broke decoding of the refund list and of a dashboard refund's webhook (repeated 400s can get the webhook disabled).
- **Should-fix findings:**
  - The lock order was the reverse of cancel's (a deadlock risk).
  - Row locks were held across HTTP calls, up to 200 s.
  - A wrong amount was only logged.
  - A second capture was kept silently.
  - The production refusal message was stale.
- **All fixed:**
  - The power is capped before the cast, and the wait capped at 60 minutes (a new test caught 64 minutes first).
  - `rzNotes` reads an object or an array.
  - The webhook locks the order, then the payment.
  - Refunds are claimed with a 5-minute lease and committed, then Razorpay is called with no transaction open, and each result is recorded in its own transaction.
  - A wrong amount, a second capture and the 40th refund failure raise `support.alert`, which opens a support incident through the existing trigger.
- **New tests:**
  - `TestEmptyNotesAreRead`
  - `TestARefundFromTheDashboardChangesNothing`
  - `TestManyFailuresNeitherOverflowNorStopTheOthers`
  - `TestAWrongAmountRaisesAnAlert`
  - `TestASecondCaptureIsPaidOnceAndAlerted` (it also covers order.paid before payment.captured)
  - `TestAnOversizeWebhookIsRefused`
- **New breaks, each caught:**
  - power uncapped: `integer out of range`
  - empty notes refused
  - second capture accepted
  - mismatch not alerted
- **Still untested:** the deadlock itself, and the staging test-payment endpoint being off with Razorpay (that is in main.go wiring).
- **Second pass:** see the PR.
