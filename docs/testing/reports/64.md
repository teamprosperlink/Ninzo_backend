# Test report: settings store (#64)

- Date: 2026-11-07
- Branch: `feat/64-settings-store`

## 1. Scope
`zones` and versioned `zone_settings`, the setting list in `internal/geo/settings.go`, and `cmd/settings` with `task settings` and `task staging:settings`. Decision 0011.

**Not covered:** reading settings from an order, which comes with orders in `v0.4.0`. Migration 0012 is not applied to Supabase.

## 3. Scenario results
| Rule | Tested |
|---|---|
| The starting values match decisions 0007 and 0011, and do not contradict each other | Yes |
| The database allows exactly the ranges the code allows, for every setting | Yes |
| A zone overrides only what it sets, and clearing falls back to the global value | Yes |
| A change is a new version. Stored versions cannot be edited or deleted | Yes |
| Every change is audited, with before, after, who and why | Yes |
| Changes that contradict, in any zone, store nothing | Yes |
| A change needs a reason and a name | Yes |
| A global change and a zone change cannot pass each other, forced with a lock | Yes |
| Nobody, including the migration login, can wipe the versions | Yes |
| Loading gives both row ids for an order to keep, read in one statement | Yes |
| The script shows, sets, audits and refuses, on a fresh database | Yes |
