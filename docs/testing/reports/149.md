# Test report: console hub operations, the server side (#149)

Date: 2026-11-13. Local Postgres only. Migration 0045 is not on Supabase (it may be renumbered at rebase: #148 takes 0044). Independent review: not yet done (to be run before the PR).

## What was built
- `internal/console/hubops.go`, mounted by `MountHubOps` in `apps/console-api/main.go`: `listHubOps` and `listStuckRestocks` (permission `hub_ops.read`: admin, ops, and a hub_manager for their own hub only) and `expireRestock` (`hub_ops.manage`: admin and ops). A hub_manager is limited as in `hubs.go`, through the user's `HubID` (`onlyHub`); one with no hub sees nothing.
- `listHubOps`: per hub (optional `zone_id`, ordered by name), the hub as in `listHubs`, the restock requests counted by state (confirmed, hub_accepted, packing, partial, ready, picked_up), `stuck`, open shortfalls (any request of the hub), quarantined lots at the hub (`lots.hub_id`, status `quarantined`) and active staff.
- Stuck: a request in confirmed, hub_accepted or packing whose `state_changed_at` is older than `restock_stuck_s` for the hub's zone (strictly longer: waiting exactly the limit is not yet stuck). `state_changed_at` is the right "waiting since" in each of the three states: it is set when the request enters the state. Partial, ready and picked_up wait on the rider, so they are never stuck. `waiting_s` is the time since `state_changed_at`.
- `listStuckRestocks`: longest waiting first, paged by (`state_changed_at`, id) with the console cursor. Each zone uses its own limit (the zones' limits are joined in with `unnest`). The rider's id and name; no phone, no customer.
- The setting `restock_stuck_s`: one line in `internal/geo/settings.go` and migration 0045 (`LOCK TABLE zone_settings` first, Up and Down; column added with a default and the default dropped, as 0034, 0040 and 0042). Default 600 seconds, range 60 to 7200, per zone. 600 and not 900: a confirmed request nobody accepts expires on its own at `restock_accept_s` (900), so with a stuck limit of 900 ops would never see it first; 10 minutes also leaves a hub time to pack. If no row holds it, the code uses 600.
- `expireRestock`: `restock.ExpireTx` (new, `internal/restock/expire.go`). It locks the request row, refuses with `restock_not_expirable` (409) unless the state is confirmed, hub_accepted, packing or partial, ends the request with `endRequest`, audits (`restock.expired_by_console`, the console user, the staff's reason, before and after state), and calls `bumpRider` (the rider's seq, the request's seq, the hub's seq, `push.rider` and a rider notification "Restock ended"). `endRequest` is the one shared piece: `ExpireUncollected` now uses it too (state, lots back on the hub's shelf, an open shortfall refused), so there is one version. A confirmed request that began as a suggestion looks like the rider's draft to `bumpRider`, which then leaves the hub's seq alone; `ExpireTx` raises it itself, as `CancelTx` does. `ended_reason` is `expired_by_console` (the staff's words are in the audit row only; the column holds 200 characters, the reason up to 500).
- The mock (`internal/mockserver/console.go`): `listHubOps` filters by `zone_id` (the second hub is in `zone_mock02`), the stuck sample waits 660 s (past the default), the expire sample shows `waiting_s` 0.

## Decision I was unsure about
The contract allows `expireRestock` in confirmed, hub_accepted, packing or partial and names one refusal, `restock_not_expirable` for any other state. It does not require the request to be stuck, and a partial request is never counted as stuck. I followed the contract: a request that is not (yet) stuck can be expired. Requiring "stuck" would need a contract change.
