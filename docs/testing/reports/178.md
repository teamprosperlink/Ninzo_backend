# Test report: #178 part A, customer app additions (contract and mock)

Date: 2026-11-12. Contract and mock only; the server side is part B. No migration.

## What was added
- Customer MenuItem: `is_veg` (boolean, required). Console AdminMenuItem: `is_veg` (required); MenuItemCreate and MenuItemUpdate: optional `is_veg` (false when left out on create).
- Customer OrderRider: `scooter_plate` (string or null, required key, max 20), beside `first_name`, shown by the same stage rule.
- `GET` and `PATCH /me/notification-settings` (`getNotificationSettings`, `updateNotificationSettings`). The customer contract's paths have no `/customers` prefix (`/me`, `/me/devices`), so these follow it. `order_updates` is always true; sending it in the PATCH is a 400.
- Customer Gate and the createGate body: optional `landmark` (1 to 80 characters) and `gate_type` (open list, schema GateType: lowercase word, up to 30 characters, known values main_gate, side_gate, tower, house, office, other). The customer contract has no gate update call, so create and read are the only places.
- Mock: sample menu items (one veg), sample gate (landmark and type), rider with plate, the notification calls, console menu echo of `is_veg`.

## Server replies that must change in part B
The server sends these as stand-ins so the database tests stay green: catalog `Item.IsVeg` (false), `orders.view` rider `scooter_plate` (null), console `scanMenuItem` `is_veg` (false). Part B must read them for real, accept `is_veg` in the console create and update bodies, build the notification settings calls, and store landmark and gate_type. Gate `landmark` and `gate_type` are optional in the contract, so the server's gate replies need no change yet.
