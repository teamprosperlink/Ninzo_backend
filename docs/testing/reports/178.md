# Part B: the server

Date: 2026-11-12. Migration 0043 (the number may change at rebase). The contract is unchanged.

## What was built
- **Veg flag.** `menu_items.is_veg boolean NOT NULL DEFAULT false`. `catalog.Item` reads it. The console menu create takes an optional `is_veg` (false when left out), update takes it (null or a non-boolean is a 400), and `scanMenuItem` returns it. The update audit row holds before and after; the create audit row says `is_veg`.
- **Scooter plate.** `view()` in internal/orders/orders.go reads `scooters.code` of the rider's shift (the same column the rider's shift reply calls `plate`): the rider's latest shift that began before the order was accepted. It goes inside the `rider` object, so it follows the first-name stage rule. Null when no shift is found.
- **Notification settings.** Table `customer_notification_settings` (RLS on, like the other tables). `GET` and `PATCH /me/notification-settings` in internal/profile/notification_settings.go: defaults off and on with no row; `order_updates`, unknown keys, nulls, non-booleans and an empty body are 400; Idempotency-Key; audit `customer.notification_settings_updated` with the switched kinds. `Deliver` in internal/orders/support.go skips a `push.customer` event with stage `ticket_reply` when `support_replies` is off, and marks it delivered. Order pushes are never skipped.
- **Gate landmark and type.** Columns on `gates` and `gate_history` (the data map says both). Validated on create (landmark 1 to 80 characters, no control or bidi characters; gate_type `^[a-z][a-z_]*$`, at most 30; explicit null is a 400, as the mock does), and the database CHECKs repeat it. Returned on read, null when not given. The console's gate edit carries them into the new history version. Erasing a customer clears the landmark (the history guard trigger gained that condition).
- Files: migrations/0043_customer_app_additions.sql; internal/catalog/catalog.go; internal/console/menu.go, gates.go; internal/orders/orders.go, support.go; internal/profile/profile.go, notification_settings.go; internal/geo/places.go; tests/db/migrations_test.go (`customer_notification_settings` added to `builtInV0100`); the data map set to v0.10.0 for the new table.

## Independent review (part B)
A separate reviewer found one bug and one weak spot. Both are fixed.
- **A settings row blocked removing an empty account.** internal/identity deletes an empty Google account's customer row when its sign-in moves to someone else, and `ON DELETE RESTRICT` turned that into a 500. It is now `ON DELETE CASCADE`. Test: `TestSettingsNeverBlockRemovingACustomer`. Putting `RESTRICT` back fails it.
- **The plate depended on two clocks agreeing.** The plate came from the rider's latest shift started before `rider_accepted_at`, which is an app-clock time, compared with a database-clock shift start. It now comes from the scooter of this rider's accepted offer for the order, so no clock is involved. Test: another shift of the same rider, started just before the accept on another scooter, leaves the plate unchanged. Putting the old lookup back fails it. The new test `TestTheScooterPlateIsNullWithoutOne` now blanks the scooter's code, because "no shift before the accept" no longer applies.
- **Contract:** `scooter_plate` maxLength is 40, as `scooters.code` allows, and the description says it is the scooter's code until real plates are recorded (test codes such as TEST-SC-KORAMANGALA-1 are 21 characters).
- **Left as gaps, in known_downsides:** no test yet covers the console gate edit carrying the landmark and type into the next version, or erasure across several gate versions.
