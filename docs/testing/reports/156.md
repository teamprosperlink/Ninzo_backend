# Test report: #156, the rider verification and route endpoints served

Date: 2026-11-11. Local Postgres only. No migration.

## What changed
Found by the rider app developer (#154): three rider contract endpoints were served only by the mock, so staging answered 404. Now served by the rider API:
- `GET /riders/me/verification`: the latest verification by the shift-start rule; `pending` with reason `not_started` before any; a verified one past its expiry is `expired`.
- `POST /riders/me/verification/start`: a stand-in until DigiLocker. It records a pending request (audited) and returns null `redirect_url` and `upload_url`; ops check the documents by hand. 409 `already_verified` or `verification_in_progress` otherwise.
- `GET /orders/{order_id}/route`: for an order this rider accepted, a straight line from the rider's last ping (or their node) to the gate, as a Google encoded polyline, with `eta_source` placeholder and no `eta_s`, until the routing engine.

## Deliberate breaks (9, each reverted)
Caught: expiry ignored; a second start while being checked; restarting a verified rider; no row stored; the route for another rider's order (first missed: the test used only an unknown order id; a second rider was added); the route from the node instead of the last ping; a measured time; a broken encoding. Two breaks first did not compile and one changed nothing; all three were redone as real changes.

Not caught alone: dropping the in-transaction save of the start reply. The idempotency middleware stores the reply itself when a handler does not, so a replay still answers the same; the in-transaction save only covers a crash between the change and the stored reply, which a test cannot easily make.

Result: PASS
