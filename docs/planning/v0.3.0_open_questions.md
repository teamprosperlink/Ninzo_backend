The owner shared five algorithm documents on 2026-11-05 and will clarify them later. **Location, availability and matching work in `v0.3.0` must not start until sections 1 to 3 are answered.** Record each answer in `docs/decisions/`, then update this file.

## 1. Which flow wins?
These documents differ from the owner's decisions of 2026-11-04, which the contracts follow.

| Topic | These documents | In force today |
|---|---|---|
| Rider accepts | Automatic, no Accept button | Rider gets an offer and accepts |
| Packing | None after the order | Rider packs while stopped, then rides |
| Timer starts | When a rider is assigned | From GPS, once packed and inside the 350 m zone |
| Rider's screen | Same countdown as the customer | Calm "1.5 mins" label, no countdown |
| No rider nearby | Customer sees "expanding the search" | Customer sees only "looking for riders" |
| Cancelling | 10-15 s free cancel after assignment, or a fee | 5 s after payment, full refund |
| Payment | Authorise, then capture | Charged up front, no holds |
| Reaching the gate | Arrive endpoint, QR or beacon check | Dropped: GPS at 100 m, OTP as proof |
| Order states | `MATCHING`, `EXPANDING_SEARCH`, `ASSIGNED`, `EN_ROUTE` | The `OrderState` list in the contract |
| System design | Microservices, Kafka or NATS | Go modular monolith, outbox by polling |

**Recommendation:** keep the 2026-11-04 decisions, because the packing step and the GPS timer protect the 90-second promise. Automatic assignment would change the contracts, the mock and the rules, and the developers would need telling.

### Two points needing a specific answer
- **Delayed customer map.** The documents lag the map on purpose, so arrival "feels faster". The contract keeps the map live. **Recommendation:** do not do this. It misleads customers and could be a consumer-law problem, so take legal advice before using it.
- **Rider loses signal mid-delivery.** The documents reassign after 15-20 s with no ping. Today's rule waits 30 s, then releases the OTP. Should the order also be reassigned, and when?

### Ideas in the documents with no rule today
- **Queueing a second order** on a busy rider, by comparing "finish this one, then go" with "bring a new rider".
- **Refilling.** A rider with an empty box is sent to the nearest hub automatically.
- **New gate pins.** Calculate the sweet spot on the spot, or refuse until it has been calculated.
- **Long waits.** Whether an order with no rider after the widest search is refused, or waits.

## 2. What is the sweet spot's time budget?
The documents give 80-85 s in the Markdown files and 55 s in the PDF. The timer is 90 s from a 350 m zone.

**Recommendation:** make it a console setting, and choose the first value from a real road test in the pilot city.

## 3. Which is the pilot city?
Map data, the road test and the routing engine all depend on it. It is also item 7 on `owner_setup_checklist.md`.

## 4. Proposed use of each algorithm
**Proposed**, until the owner confirms it.

| When | Algorithms | Why |
|---|---|---|
| Already covered | Reservations with expiry, row locks, idempotency, fencing tokens, order state machine, OTP, two-ping check | In the contract and tables, or in the next `v0.2.0` steps |
| `v0.3.0` to `v0.5.0`, with the APIs | H3 resolution 10, sweet spot lookup, filter and rank riders, 100 m and zone checks, impossible-jump GPS filter | Availability and matching are empty without them |
| Offline, before the pilot | Reachable area for each gate, using Valhalla or OSRM, in `tools/` | Runs in the background, not during an order. Needs the pilot city |
| After real data | p50 and p90 travel times, staging node placement, Kalman filter, map matching | Useless without real trips |
| Skip for the pilot | Hungarian, min-cost flow, bottleneck assignment, subset enumeration, ILP, OR-Tools, quantile regression, ML, Kafka | With 4-8 scooters and 1-3 items, simple ranking is enough and easier to debug |
| Never written by us | Dijkstra, A*, Contraction Hierarchies, RPHAST | They come inside the routing engine |

## 5. To do when `v0.3.0` starts
- **Road test first.** Run reachable-area calculations on real roads in the pilot city, before building matching on any time budget.
- **H3 in Go.** From memory, the Go H3 library needs C code, which clashes with `CGO_ENABLED=0` and the small image in `deploy/Dockerfile.service`. Check this before choosing a library.
- **Routing engine.** Choosing between Valhalla, OSRM and Google Routes is still open in `tech_stack.md`.
- **Part-time riders.** The application flow is planned for `v0.3.0` (`authentication_rules.md`, section 11).
